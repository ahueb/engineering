# Risk register

Owner for every item: alan@hueb.org unless stated. Reassess at each minor release or when the trigger fires.

| ID | Risk | Status | Mitigation / compensating control | Trigger to reassess |
|---|---|---|---|---|
| R1 | Distribution channel: consumers who track `main` get whatever is pushed; a compromised maintainer account ships a hook into every session | Partially mitigated | `main` requires the `linux` GitHub Actions status check (applied 2026-09-12); a required check rejects an unchecked direct push, including from the maintainer, so every commit on `main` has run the `./ci.sh` it carries on a tree identical to what was reviewed. This is a regression gate, not an integrity gate against a compromised maintainer account: the check runs the PR's own `ci.sh` and `scripts/ci/*`, and the only code owner is the maintainer, so a hostile PR can make its own check pass. `actions/checkout` is pinned by commit SHA with `persist-credentials: false`, and the runner never executes an unverified installer (see SECURITY.md). Traded away for this: commits on `main` are GitHub-signed by the squash merge, not signed by the maintainer's own key, so per-commit maintainer attestation on `main` is weaker than before — attestation now lives in the signed release tag instead (see SECURITY.md, "two proofs"). Branch protection (linear history, no force push or deletion, admins enforced) and `.allowed_signers` for tags are unchanged | Signing key rotation; any change to branch protection or the required check; a second maintainer with push access |
| R2 | No server-side CI: a push that skips the pre-push hook (`--no-verify`, or a clone without `core.hooksPath`) is unverified | Closed | GitHub Actions is now the server-side gate: the `linux` job is a required check on `main`, so a pusher cannot skip it the way the local `pre-push` hook could be skipped. `.githooks/pre-push` remains as a fast local gate for non-release pushes | Removal of the required check |
| R3 | Model-facing behaviour (skill triggering, agent conduct) is checked only by the 20 trigger evals, which grade tool invocation, not output quality, at one run per case | Partially mitigated | 20/20 recorded in `plugins/engineering/evals/RESULTS.md` on the current tree (2026-09-12); outcome-graded for `production-readiness-review` (`behaviour-prr-1`..`-7`, 6 of 7 scenarios pass at 3 runs; scenario 4's bounded-canary case is open, see R15) and `comment-cleanup` (`behaviour-comment-cleanup`, 3 of 3 runs pass once `Skill` is granted; an earlier 2-of-3 batch was a missing grant, not a flake); other skills remain trigger-graded only | Any change to a skill description or the set of model-invocable skills; Claude Code changes the skill listing budget; a new model becomes default; a repeat of the scenario-4 or harness-flake failure |
| R4 | Single maintainer: recovery, release, and marketplace knowledge held by one person | Accepted | README and `release.sh` document the full release path; repo is public and forkable; MIT licence | A second contributor with push access |
| R5 | Hook and script portability across platforms | Partially mitigated | `.github/workflows/ci.yml`'s three-job matrix now proves exactly this, per platform, on every PR and push: `macos` (macos-latest) forces every `#!/usr/bin/env bash` script onto the system's real bash 3.2 (a `bash` → `/bin/bash` PATH shim, version asserted in the job log) and runs the full default `ci.sh` tier there, so the hook, `install.sh`, `release.sh`, and their scratch scenarios are proven under bash 3.2, not merely reviewed for compatibility. `windows` (windows-latest) runs the Python unit tests under `python -X dev` (the eight symlink-resolution and replace-open-file tests are skipped there as POSIX-only, matching the scope below) and a `bash -n` syntax pass under Git Bash on the shell scripts, but does not run the `ci.sh` scratch-install scenarios there. The matrix therefore does not prove: `install.sh`'s Windows behaviour when `os.replace` fails because Claude Code holds the target file open (still only reported as "close Claude Code and rerun", not exercised); MSYS-style symlink resolution on Windows (explicitly out of scope, not just untested); or any Windows scratch-install scenario (rollback, restore disclosure, stamps) actually running | A Windows scratch-install failure report; a decision to add a Windows scratch-install job |
| R6 | Claude Code version drift: `fable` alias, `[1m]`, `effort` frontmatter, skill listing budget changed across 2.1.173–2.1.267 | Accepted | README pins minimum 2.1.267 (2.1.269 for `claude plugin eval`) and names the behaviours that depend on it | Any Claude Code changelog entry touching aliases, effort, plugins, or hooks |
| R7 | Consumer rollback: the plugin-version install form does not pin | Mitigated | Marketplace `@ref` pinning (`ahueb/engineering@vX.Y.Z`) verified 2026-09-12 and documented; directory-marketplace path kept for local signature verification | Claude Code adds version resolution for marketplace installs |
| R8 | `--purge-official` deletes previously registered official-marketplace and official-plugin entries from the user's settings. (`--no-official` alone is no longer destructive: it only skips adding new official entries and leaves existing ones untouched — a behaviour change from earlier releases, see CHANGELOG.) | Accepted | `--purge-official` is opt-in and documented as destructive in README; an explicit `false` opt-out is kept; a backup is written before the change | User report of surprise |
| R9 | EU Cyber Resilience Act applicability assumed out of scope (non-commercial open source) | Open | None needed while non-commercial | Any monetisation or bundling into a commercial product |
| R10 | Policy loads twice in three windows: (a) a session already running an older plugin hook version when the policy migrates from `CLAUDE.md` to the rules file keeps injecting the plugin copy via the hook until it restarts, because both the rules file and its own in-session hook version are now present; (b) a user who declines migration but later adds `rules/engineering-policy.md` by hand ends up with both a legacy `CLAUDE.md` policy copy and a rules file, each loaded independently; (c) the installer itself could in principle create both a `CLAUDE.md` policy copy and a rules file in the same run | Accepted | Case (a): the installer's summary prints "restart Claude Code" after every migration; a session started before migration still injects the plugin's hook copy once, until restart — this part of case (a) remains and is not itself a defect. Case (b): the hook checks both `rules/engineering-policy.md` and `CLAUDE.md` for the header and stays silent when either already carries it, so the hook itself never double-injects; the duplication in case (b) is two independently-loaded policy copies, not a hook defect, and is inherent to a user hand-editing config outside the installer. Case (c): the installer guard that refuses to write `CLAUDE.md` when `rules/engineering-policy.md` is already installed (and vice versa via migration/`--policy-target`) prevents the installer from creating this duplicate itself | Any user report of a duplicated policy in one session |
| R11 | The interactive-accept branch of the legacy-policy migration prompt (confirmed on a TTY) is exercised in CI only when Python's `pty` module works on the host; on hosts where it does not, that scenario is skipped rather than run | Accepted | The decline path, `--yes`, and `ENGINEERING_NO_PROMPT=1` are exercised unconditionally in CI; the accept branch is verified manually on hosts where `pty` is unavailable | A CI host change that makes `pty` reliably available everywhere, or a user report of the accept branch misbehaving |
| R12 | Capability boundaries for agents/skills that inspect but should not mutate | Mitigated for `test-triage`, `browser-tester`, `docs-check`, `literature-review`; narrowed for `deep-audit` | `test-triage` and `browser-tester` no longer have Bash at all (tool-list boundary, not instruction). `docs-check` and `literature-review` carry `disallowed-tools: Bash, PowerShell, Edit, Write, NotebookEdit, Agent, Skill, Artifact` (a tool-list boundary; `disallowedTools: Bash(...)` removes the whole tool, not a pattern within it). `deep-audit` now forks to the plugin agent `engineering:auditor`, which keeps Bash but restricted by the plugin `PreToolUse` hook `hooks/readonly-guard.sh` to an allowlist (`hooks/readonly-allowlist.txt`) keyed to that agent type; this is a real interception of the tool call, not an instruction, but it is an accidental-mutation guard, not a sandbox against a hostile repository or an adversarial auditor (see SECURITY.md, R14). The `agent_type` value `engineering:auditor` was observed in a live PreToolUse payload from a `/engineering:deep-audit` run of this plugin, in which the guard denied `touch` (payload recorded in `ci/fixtures/pretooluse-payload.json`, which `ci.sh`'s guard table feeds to the guard); the guard fails closed for the auditor when its own machinery is unavailable, and open for every other agent. Confidentiality is out of scope: allowlisted read commands can print any readable file into the audit report. Reviewers that judge code (`semantic-reviewer`, `security-reviewer`, `plan-auditor`, `architect`, `scout`) still have no Bash by tool list; README and `context/CLAUDE.md` state which agents have a shell and which are guarded | A constrained command-runner tool becomes available; a reported injection incident; a reported guard bypass |
| R13 | Tag pushes (`refs/tags/v*`) are not gated by the required status check the way branch pushes to `main` are; `release.sh tag` and `pre-push`'s release skip both depend on `gh` and GitHub being reachable and correctly authenticated | Open | `release.sh tag` only tags a commit that already carries the subject `Release engineering X.Y.Z` and whose `plugin.json` matches — i.e. a commit that already went through the required-check-gated PR merge — so an ungated tag push cannot introduce new, unchecked code, only re-point or duplicate a tag on an already-checked commit. `gh` unavailability degrades `prepare`/`pr` to a printed manual-steps exit 1, not a silent skip (proven by a `ci.sh` scenario). The `pre-push` skip is keyed to the ambient `ENGINEERING_RELEASE=1` variable: `release.sh` sets it only for its own push commands, but a user who exports it in a shell profile (the manual-steps text prints it inline) silently disables the local gate for every later release-branch or tag push; an empty ref list or a ref deletion never skips the gate. A GitHub tag protection ruleset (requiring the pusher to match a pattern, or requiring linear ancestry from `main`) would close the pure ungated-tag-push surface but is not configured | A tag pushed that does not correspond to a checked `main` commit; GitHub adds a lower-friction tag-protection mechanism |
| R14 | The `readonly-guard.sh` allowlist (`hooks/readonly-allowlist.txt`) is a plain-text data file, editable independently of the guard's code and its stated intent | Accepted | The allowlist is scanned by `ci.sh`'s guard table (allowed and denied samples, including quoted, backslash-escaped, `$IFS`-split, `find -fprint0`, `rg --pre`, and `file -C` forms found by the 2026-09-12 audit); its header documents the format and the accidental-mutation-only property; README/SECURITY state the same limit | Any change to `hooks/readonly-allowlist.txt` not reviewed against the guard's intent; a reported guard bypass through an allowlisted token |
| R15 | The `production-readiness-review` rubric's bounded-canary rule returns `VERDICT: NOT READY` for scenario 4 (a 1% internal canary behind a kill switch) where the scenario's expected verdict is `CONDITIONALLY READY`, on all 3 measured runs (see `evals/behaviour-prr-4`) | Open | Measured, not assumed: the `VERDICT`/`GATE` regex graders and the scenario's `llm` rubric both confirm the skill consistently returns `NOT READY` rather than a grader miscalibration. Whether the rubric or the scenario's expectation is wrong is an open decision, not yet made | A decision on the bounded-canary rule; a rubric or scenario change; a rerun that reproduces or contradicts the 3/3 result |
