# Security

This plugin runs code on your machine: a SessionStart hook (`plugins/engineering/hooks/session-start.sh`) at every Claude Code session start, `install.sh` when you install, and `repo_probe.py` when the readiness review runs. Treat it like any other software you execute.

## Reporting a vulnerability

Email alan@hueb.org with the subject `engineering plugin security`. Include the version (`claude plugin list`), the file or behaviour affected, and reproduction steps. Do not open a public issue for an unpatched vulnerability.

Expected response: acknowledgement within 7 days; a fix or mitigation for a confirmed issue in the next release, normally within 30 days. This is a single-maintainer project with no paid support; those are intentions, not a service-level commitment.

## Verifying what you install

- Every release is a signed tag `vX.Y.Z` on `main`. Verify with the committed allowed-signers file:

  ```bash
  git config gpg.ssh.allowedSignersFile .allowed_signers
  git tag -v v2.7.1
  ```

- `main` is branch-protected on GitHub: linear history, no force pushes, no deletions, enforced for admins, and a required status check (`linux`, GitHub Actions app id `15368`) — direct pushes of an unchecked commit to `main`, including from the maintainer, are rejected.
- The required check is a regression gate, not an integrity gate: the workflow runs the candidate tree's own `ci.sh` and `scripts/ci/*`, so a PR that rewrites those files can make its own check pass, and the sole code owner is the maintainer. What it does prove is that no commit reaches `main` without a green run of whatever `ci.sh` that commit carries; it does not defend against a compromised maintainer account. The required check and the tag prove two different things, not one. The required check proves `./ci.sh` passed on a tree identical to `main`'s head at merge time (the check runs on the PR head commit, and `strict: true` on the required check keeps the merged tree identical to what was checked; a rebase merge does not change the tree, only the SHA and the signer). The signed tag proves the maintainer released that exact commit; it says nothing about whether `ci.sh` passed. Trust both, or neither, but do not treat one as evidence of the other.
- Commits on `main` are GitHub-signed as a side effect of the rebase-and-merge that closes every release PR, not signed by the maintainer's own key; `.allowed_signers` (below) verifies release *tags*, which the maintainer signs directly, not commits on `main`.
- Tag pushes are not covered by the required check: `refs/tags/v*` is a push trigger for CI, but a tag push cannot be blocked by a branch-protection required-status-check the way a branch push can, so a signed tag is evidence the maintainer released that commit, not evidence CI ran on the push of the tag itself (it already ran on the PR that produced the commit). This is a known residual; see the risk register, R13.
- Every push to a non-release branch is also gated locally by `./ci.sh` through a pre-push hook (bypassable with `--no-verify`, or absent entirely without `git config core.hooksPath .githooks`); the required check on `main` is the check that cannot be bypassed by the pusher.
- Pin a version instead of tracking `main` by registering the marketplace at a signed tag (`claude plugin marketplace add ahueb/engineering@vX.Y.Z`), or by checking out the tag and registering the clone as a directory marketplace when you want to verify the signature locally (steps in README, "Verify, pin, and roll back"). The `engineering@engineering@<version>` install form does not pin.

## What the CI runner trusts

Every job in `.github/workflows/ci.yml` installs Claude Code at the exact version pinned in `scripts/ci/claude-version.txt`, and refuses to proceed on any mismatch: it imports the vendored Anthropic release key (`scripts/ci/anthropic-release-key.asc`, fingerprint `31DDDE24DDFAB679F42D7BD2BAA929FF1A7ECACE`), checks that fingerprint against the value hardcoded in `install-claude.sh`/`install-claude.ps1`, asserts that exactly one primary key was imported, downloads that version's `manifest.json` and verifies its signature with `gpg --status-fd`, requiring a `VALIDSIG` line bound to that fingerprint, then downloads the platform binary named in the verified manifest directly from the release bucket and verifies its SHA256 and size against the manifest before it is placed on `PATH` or executed. No convenience installer (`claude.ai/install.sh`) is fetched or run. `actions/checkout` is pinned to a commit SHA with `persist-credentials: false`. The vendored key's fingerprint was established from the key published at the documented fixed URL (`https://downloads.claude.ai/keys/claude-code.asc`) and cross-checked against the apt repository signing key Anthropic documents for its Debian/Ubuntu package repository. No job in the workflow uses secrets or configures credentials; `--full` (which needs an authenticated CLI) never runs in Actions.

## The readonly guard's limits

`plugins/engineering/hooks/readonly-guard.sh` restricts the `engineering:auditor` agent's Bash (used by `/engineering:deep-audit`) to an allowlist of read-only inspection commands (`plugins/engineering/hooks/readonly-allowlist.txt`), denying redirection, backticks, any `$`, any backslash, and background `&` outright, and tokenising each simple command with shell quoting rules before the allowlist's argument checks are applied (so `"-o"` is the same as `-o`), and denying unquoted brace, glob, and tilde characters, which the shell would expand after the guard has seen the text. Long options are matched by prefix because getopt-style tools accept any unique abbreviation. The guard fails closed for the auditor: if `python3` is missing, the guard program crashes, the hook input is not JSON, or `tool_input` carries no `command` string, the auditor's command is denied while every other agent is unaffected. This is an accidental-mutation guard, not a sandbox: it assumes the auditor itself is not adversarial and that the repository it inspects is not actively trying to defeat the guard. Confidentiality is out of scope: allowlisted read commands (`cat`, `grep`, `jq`, ...) can read any file the user can, and whatever they print enters the auditor's report. It does not stop a repository-controlled build/test runner invoked some other way, or an interpreter reachable through an allowed token's arguments — none of `bash -c`, `eval`, `env`, `xargs`, `sed`, or `awk` are on the allowlist, and the allowlist itself is a plain-text file (data), so it can drift out of sync with the guard's intent without a code change flagging it.

## What the code does and does not do

- Never sends data anywhere. The hook prints a local file; the probe writes JSON to stdout only.
- The probe never prints file contents, never follows symlinks, skips secret-looking file names, and runs `git` with `core.fsmonitor` and `core.hooksPath` disabled so a hostile repository cannot execute commands through it.
- `install.sh` reads `settings.json`, `CLAUDE.md`, and `rules/engineering-policy.md` under your config directory, plus the output of `claude plugin marketplace list --json` and `claude plugin list --json`, to decide what to merge or migrate. It writes `settings.json` (merged with `settings.recommended.json`), the policy as `rules/engineering-policy.md` (or `CLAUDE.md` with `--policy-target claude-md`), and the installer marker `engineering-installer.json`. Before any file it is about to change, it copies that file into `~/.claude/backups/engineering/<stamp>/` (directory mode 0700; the newest 5 stamps are kept). `settings.json` can hold API keys, MCP server credentials, or other secrets you have configured, so treat the backup directory with the same care as `settings.json` itself. The drift report and `--dry-run` diff redact `env` values, any key containing `key`, `token`, `secret`, `password`, or `credential`, and `apiKeyHelper` as `<redacted>` before printing. It refuses to run if the marketplace cannot be registered, if `settings.json` is unreadable or malformed, if a target is a hard-linked file (unless `--break-hardlinks`), or if `settings.json` is a dangling symlink (unless `--create-through-dangling`).
- File permissions: the installer preserves the existing mode of a `settings.json` it did not create; it only sets 0600 on a `settings.json` it creates from nothing during the run. If you created `settings.json` yourself earlier (for example with the Claude Code CLI under a permissive umask), it keeps whatever mode it already had — the installer does not tighten a pre-existing file's permissions. Run `chmod 600 ~/.claude/settings.json` yourself if the file holds secrets and its mode is wider than you want.
- `./install.sh --restore [STAMP]` first takes its own pre-restore backup (under a new stamp) of every file it is about to overwrite, then restores regular files unconditionally from the chosen backup. It validates the backup manifest, including that stored filenames are flat (no path traversal). A backed-up symlink whose target is now missing is recreated only when the recorded target path already exists on disk with content identical to the backup. A file that resolves outside your config directory (through a symlinked file or parent directory) is overwritten only when it already exists there and is disclosed with an `outside config dir:` line first (refused entirely with `--no-outside-cfg`); restore never creates a file or directory outside your config directory, and refuses that entry otherwise. Restored file modes are masked to permission bits only.

Only the latest released version receives fixes.
