# Implementation loop

1. Restate the requested outcome and hard constraints in working terms. For a written plan with several tasks, switch to `/engineering:plan-execution`, which fans every task out to parallel `engineering:bulk-implementer` agents and verifies once after merge.
2. Inspect the repository before editing. Discover the relevant architecture, existing patterns, test commands, CI checks, and configuration from source files rather than guessing. Include relevant comment contracts and consumers in this discovery when documentation is in scope. Dispatch independent discovery questions (call sites, tests, migrations, config) to `engineering:scout` agents in one batch and keep only their conclusions.
3. Identify uncertainty that can be resolved from the repository or authoritative documentation. Resolve it before implementation when it could change the design. When resolving uncertainty, inspect relevant comment contracts and consumers, not only code behavior.
4. Plan only enough to make the next actions coherent. Prefer the smallest design that satisfies the requested behavior and preserves existing interfaces unless change is required.
5. Implement in focused increments. Avoid unrelated cleanup, dependency churn, configuration weakening, or speculative abstraction. Preserve relevant contracts and rationale when editing code. Update comments/docstrings invalidated by the requested behavior change in the same scoped change; do not normalize an unresolved implementation/contract conflict. When authoring material contract documentation, changing consumer-sensitive comments, or resolving such a conflict, read `${CLAUDE_PLUGIN_ROOT}/skills/comment-cleanup/references/comment-guidance.md`. Do not invoke repository-wide comment cleanup for ordinary implementation.
6. Add or update tests where they materially improve regression detection. Use test-first development when it clarifies behavior or reproduces a bug; if the `superpowers:test-driven-development` skill is available, invoke it for that red/green cycle. Do not force TDD when it adds no value. For a bug with an unclear cause, use `superpowers:systematic-debugging` before editing.
7. Run the narrowest meaningful verification first, then broaden to repository-standard checks when practical. Run independent checks concurrently in the background and collect all results before judging. When the change is visible in a web UI, confirm it through `/engineering:browser-testing` rather than inferring from unit tests.
8. Inspect the final diff for accidental changes, debug code, generated artifacts, weakened assertions, missing error paths, silent behavior changes, documentation drift, or unintended consumer changes.
9. Use a fresh review perspective (`engineering:semantic-reviewer`) only when change breadth, uncertainty, or failure cost warrants the extra call and deterministic checks do not already cover the property. Delegate to `engineering:security-reviewer` for changed trust boundaries or sensitive data paths. When both reviews apply, dispatch them together in one batch. For a single change, implement in this context.
10. Do not claim completion without evidence. Run `/engineering:verification-loop` for the final check, and `/engineering:checkpoint` if the work is handed to another session or a `/engineering:plan-execution` run. Report what passed, what was not run, and any residual risk.
